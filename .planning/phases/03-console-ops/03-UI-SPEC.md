## Spacing Scale

Identical to Phase 2. No new exceptions for Phase 3.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap, badge internal padding, spinner offset |
| sm | 8px | Compact row padding, button gap, table cell padding |
| md | 16px | Card / panel internal padding (horizontal), form field spacing |
| lg | 24px | Panel section gap, slide-over internal section gap |
| xl | 32px | Column gap, slide-over top padding |
| 2xl | 48px | Sidebar section gap |
| 3xl | 64px | Page-level top padding |

**Phase 3–specific exceptions:**

- Two-panel client detail (`/ops/clients/{id}`): each panel uses `h-[calc(100vh-3.5rem)] overflow-y-auto` — the 3.5rem (56px) subtracts the sidebar header bar. Each panel scrolls independently.
- Requisition detail scrollable hub: section spacing between major blocks (Fields → Shortlist → Interviews → Placements) uses `mt-8` (32px) / `mb-4` (16px) section dividers with a `<Separator />` at each boundary.
- Shortlist table row height: `h-10` (40px) — denser than default shadcn table to keep all four sections above the fold on initial load.
- Interview row height: `h-10` (40px) — same density as shortlist.
- Notes log entry vertical spacing: `gap-3` (12px) between timestamped note items — between `sm` (8px) and `md` (16px); closest valid multiple is 12px (3 × 4).
- Notes textarea: `min-h-[80px]` — sufficient for multi-line paste, not excessively tall.

## Typography

Identical scale to Phase 2. No new type roles introduced.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Body | 14px (0.875rem) | 400 (regular) | 1.5 | Table cells, panel field values, notes text, form labels, list row copy, sidebar nav labels |
| Label / Meta | 12px (0.75rem) | 400 (regular) | 1.4 | Timestamps, badge text, muted metadata (client name in req list, status labels), section headers in slide-over |
| Subheading | 16px (1rem) | 600 (semibold) | 1.4 | Panel section headings ("Client Fields", "Notes Log", "Shortlist", "Interviews", "Placements"), table column headers, page section titles |
| Heading | 20px (1.25rem) | 600 (semibold) | 1.2 | Page title ("Clients", "Requisitions", "Interviews"), client name in detail page header, req title in detail page header, slide-over entity name |

**Weights used:** 400 (regular) and 600 (semibold) only. No 500/700 in this phase.

**Phase 3–specific notes:**

- JD textarea placeholder: 14px/400, `text-muted-foreground` — standard body with muted color.
- Fit score column in shortlist table: 14px/600 — semibold to signal it is the primary sort key.
- Req status badge (Open / Filled / Closed): 12px/400 (`Label / Meta` role) — same as Phase 2 status badges.
- Parse status text ("Parsing JD…" / "Parse failed"): 12px/400, rendered below the JD textarea, not as a badge.
- Note timestamp in notes log: 12px/400, `text-muted-foreground`, ISO-relative format ("2 hours ago").
- Fit score large display (Candidate Detail Sheet): 20px/600, brand blue (`text-primary`) — uses existing Heading role; semibold weight and accent color provide sufficient visual prominence without introducing a 5th font size.

## Interaction Contracts

### JD Parse Flow (D-05, D-06, D-07)

1. User completes Create Requisition form (client, title, JD text) and clicks "Create Requisition".
2. Button enters "Creating…" disabled spinner state. Form cannot be resubmitted.
3. POST `/api/v1/ops/requisitions` fires. On 201 success, POST `/parse-jd` fires immediately.
4. Dialog remains open. "Create Requisition" button transitions label to "Parsing JD…" (still disabled).
5. Parsed fields group appears (below Separator) but fields show Skeleton shimmer, all inputs `disabled`.
6. `useAsyncJob` polls GET `/api/v1/ops/requisitions/{id}` every 2 seconds with `statusMap: { open: 'complete', filled: 'complete', closed: 'complete', parsing: 'pending' }`.
7. On `phase === 'complete'`: Skeletons replaced by actual inputs with parsed values. Fields animate in (cascade stagger as described). Parse status line clears. Button enables for "Go to Requisition" action that routes to `/ops/requisitions/{id}`.
8. On `phase === 'failed'`: Fields unlock as empty inputs (user fills manually). Parse status line shows error text. Sonner toast: "JD parsing failed — fill fields manually." Dialog stays open.
9. User always ends up on `/ops/requisitions/{id}` — whether via parse-complete auto-navigate or manual "Go to Requisition" after filling fields.

### Shortlist Row Actions (D-09) — Optimistic with Undo

1. User clicks Approve / Hold / Pass icon button on a shortlist row.
2. Status badge on that row immediately updates to target state (optimistic).
3. PATCH `/api/v1/supply/shortlists/{submission_id}` fires.
4. Sonner toast: "Candidate [name] approved." / "Marked as hold." / "Passed on [name]." with "Undo" action, duration 5000ms.
5. If Undo clicked: fire compensating PATCH with previous status; badge reverts.
6. If PATCH fails: toast upgrades to "Failed to update — try again." Badge reverts.
7. No exit animation on row (candidate stays in table; status badge updates in place).

### Interview Status Inline Select (D-13)

1. Ops rep opens Select on interview row. Options shown: all valid transitions from current state.
   - Scheduled → [Accepted, Declined]
   - Accepted → [Completed]
   - Declined → [no further transitions — Select disabled, shows "Declined"]
   - Completed → [no further transitions — Select disabled, shows "Completed"]
2. On selection: PATCH fires immediately (no confirmation step for non-destructive transitions).
3. Status badge on row updates optimistically.
4. If PATCH returns 409: Select reverts to previous state, toast: "Invalid status transition."
5. If PATCH succeeds: `queryClient.invalidateQueries` on interviews query for this req.

### Notes Append Flow (D-16)

1. Ops rep types or pastes into Textarea in the right panel.
2. "Add Note" button enabled as soon as ≥1 character present.
3. On click: POST `/api/v1/ops/clients/{id}/notes` with `{ text, channel: 'other' }`.
4. On success: Textarea clears. New note appears at top of notes log (reverse-chronological prepend). `queryClient.invalidateQueries` on client-notes query.
5. On failure: Textarea content preserved. Toast: "Failed to save note — try again."

### Placement Log Submission (D-14, D-15)

1. "Log Placement" button on req detail opens Sheet slide-over.
2. Candidate/req/client fields are pre-filled and read-only.
3. User fills fee, billing status (required), retention flag.
4. Submit: POST `/api/v1/ops/placements`. Sheet closes on success.
5. Sonner toast: "Placement logged for [Candidate Name]."
6. Placements section on req detail refetches and shows new placement row.
7. On failure: Sheet stays open. Toast: "Failed to log placement — try again."

### No Keyboard Navigation in Phase 3

Phase 3 Ops flows are form-heavy and read-heavy, not queue-driven. J/K navigation is not introduced for client or requisition lists. Keyboard focus follows standard browser Tab order within forms and tables. The `?` shortcut overlay from Phase 2 is not extended for Ops in this phase.
