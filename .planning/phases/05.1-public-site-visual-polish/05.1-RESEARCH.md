## Summary

Phase 5 shipped a functionally complete public site against MSW mocks. The implementation used correct token references (`border-border`, `text-muted-foreground`, `bg-card`, etc.) throughout, but the result is a shadcn utility default appearance — clean but generic. The six target surfaces each have specific, concrete issues documented below.

The token layer in `packages/ui/src/styles/theme.css` is the correct entry point: it controls the palette, radius, and ring colour for the entire system. No `--radius` token is defined there (only in `apps/web/globals.css` as `--radius: 0.5rem`), meaning radius changes must happen at the app level. The background is pure white (`oklch(1 0 0)`) — Contrario.ai uses `#FAFAF9` (near-white warm), which is a small but perceptible warmth difference.

The largest visual wins are achievable without touching any `packages/ui/src/components/ui/` files: the locked-jobs overlay, resume dropzone, hero CTA button colour, and card hover lift can all be done in `apps/web` files alone.

**Primary recommendation:** Token changes first (theme.css + globals.css), then surface-by-surface component edits in apps/web only. The work naturally splits into two waves: Wave 1 = token layer + hero + job cards; Wave 2 = auth/onboarding forms + dropzone + overlay.

## Surface-by-Surface Audit

### Surface 1: Landing Hero (`apps/web/app/_components/hero-section.tsx`)

**Current implementation:**
```tsx
<div className="flex max-w-[900px] flex-col items-center text-center" style={{ paddingTop: '120px' }}>
  <h1 className="text-[120px] font-light leading-[1.05] tracking-[0.04em] text-foreground">
    The talent platform built for you.
  </h1>
  <p className="mt-6 text-base leading-relaxed text-muted-foreground">...</p>
  <Button asChild size="lg" className="mt-8">
    <Link href="/signup">Join the talent pool</Link>
  </Button>
</div>
```

**Issues found:**
1. `style={{ paddingTop: '120px' }}` — inline style. Should be Tailwind: `pt-[120px]` or `pt-28`.
2. `Button` uses `variant="default"` which renders `bg-primary`. If primary becomes a warm/neutral colour (per the token audit), this becomes the one accent CTA. If primary stays blue-violet, this is the wrong colour.
3. `text-[120px]` — large display text. Good. The `font-light` (weight 300) is the editorial look. This is working correctly.
4. `max-w-[900px]` — limits container. For 120px text, this means roughly 7-8 characters per line — editorial and correct.
5. No transition or hover state on the CTA — Button component handles `hover:bg-primary/90` via `buttonVariants`. Fine.
6. Background is inherited white — once warm background override is applied to body/root, this page will warm up automatically.

**Specific changes needed:**
- Replace `style={{ paddingTop: '120px' }}` with `pt-28 md:pt-[120px]`
- Add `gap-y-0` or letter-spacing refinement to headline if visual review shows issues
- The button colour is entirely dependent on the primary token decision (locked in token wave)

**POL-01 gate:** Editorial typography already exists (120px, font-light, tracking). The "no gradient" constraint is already met — no gradient in the hero. The accent CTA issue is the token question.

### Surface 2: Job Board Cards (`apps/web/app/jobs/_components/job-card.tsx`, `apps/web/app/jobs/page.tsx`)

**Current implementation:**
```tsx
<Card className={cn(
  'cursor-pointer p-4 transition-colors hover:bg-muted',
  isLocked && 'blur-[4px] pointer-events-none select-none',
)}>
```

**Issues found:**
1. `hover:bg-muted` — flat colour swap. No translateY lift, no shadow change. Looks "cheap."
2. `transition-colors` — correct (not `transition-all`). But no duration specified — defaults to Tailwind 150ms. Add `duration-150` for explicitness.
3. `p-4` — overrides the shared Card's `py-6` default. This means the Card component's built-in gap-6 between child sections is suppressed. Card becomes a raw container with `p-4`. Acceptable for tight cards.
4. `shadow-sm` — the shared Card component has `shadow-sm` baked in. No hover shadow change.
5. `rounded-xl` — Card has `rounded-xl` baked in. Correct.
6. Inside the card: `text-base text-foreground` for title (good), `text-sm text-muted-foreground` for company/location (good). The `space-y-2` inside creates compact stacking.
7. Badge `variant="secondary"` for employment type — secondary is `bg-secondary` = `oklch(0.961 0 0)` which is barely distinguishable from white. Low visual contrast. Could use `variant="outline"` for a more intentional look.
8. `MapPin` icon at `h-4 w-4` — correct size.
9. Missing: hover state for the Link wrapper — the link itself has no `focus-visible` style.

**Specific changes needed:**
- Change hover from flat `hover:bg-muted` to lift pattern:
  ```tsx
  'cursor-pointer p-4 transition-colors transition-shadow duration-150 ease-out hover:bg-muted/50 hover:shadow-md hover:-translate-y-px'
  ```
  Note: Combining `transition-colors` and `transition-shadow` requires Tailwind 4's `transition-[color,box-shadow,transform]` or separate properties.
- Add `group` to Link, `group-focus-visible:ring-2 group-focus-visible:ring-ring` to Card for keyboard nav.
- Consider `border-border/60` on Card for slightly softer border vs inherited default.
- Add `ease-out` explicitly to all transitions.
- Filter bar `h-14 border-b border-border` — the filter bar border creates a visual separator. This is fine but `border-border` at full opacity looks like a hard line. Consider `border-border/70`.

**Grid layout (jobs/page.tsx):**
- `grid grid-cols-1 gap-4 md:grid-cols-2 xl:grid-cols-3` — correct responsive grid. `gap-4` is tight (16px). Can remain or increase to `gap-5` (20px) for more breathing room.

**POL-02 gate:** Hover state must change from flat colour to lift. Border must remain soft (already is). Spacing: current is acceptable but gap could increase 4px.

### Surface 5: Resume Upload Dropzone (`apps/web/app/onboarding/1/page.tsx` lines 103–115)

**Current implementation:**
```tsx
<label className="flex min-h-[180px] cursor-pointer flex-col items-center justify-center rounded-2xl border border-dashed border-border bg-card px-6 text-center transition-colors hover:bg-accent/40">
  <span className="text-sm font-medium text-foreground">

  </span>
  <span className="mt-2 text-xs text-muted-foreground">PDF, DOC, DOCX up to mock limit</span>
  <input type="file" accept=".pdf,.doc,.docx" className="sr-only" ... />
</label>
```

**State coverage found:**
- `status: 'idle'` — static label above shows default text. Visual: basic dashed box.
- No drag-over state (no `dragover`/`dragenter` event handler; the dropzone is a plain `<label>`, not a react-dropzone component)
- `status: 'uploading'` — button text changes to "Working…". Visual: label still looks idle.
- `status: 'processing'` — "Parsing your resume..." text appears below. Visual: label still looks idle (no uploading animation).
- `status: 'failed'` — error text appears. Visual: label still looks idle.
- File selected (any status): `file.name` replaces default text. No visual confirmation of file type/size.

**The fundamental issue:** The dropzone is a raw `<label>` with no event handlers for drag. It has no crafted visual states. The label just does a static hover colour change. This is the "raw dashed-border utility default" the user wants replaced.

**Proposed redesign approach:**

The CONTEXT.md `<specifics>` section does NOT mandate react-dropzone (that library is already in the stack for the console's import dropzone). For the public onboarding, the current approach uses a plain `<label>` with a hidden `<input type="file">`. We can craft the visual states without adding react-dropzone by:
1. Using HTML5 drag events (`onDragEnter`, `onDragOver`, `onDragLeave`, `onDrop`) on the `<label>` element
2. Tracking `isDragOver` in local state
3. Creating explicit state classes for each status

**Specific changes needed — extract to `apps/web/app/onboarding/_components/resume-dropzone.tsx`:**

```tsx
// State: idle
className="border-border/70 bg-card"
// → Upload icon (lucide UploadCloud), headline text, subtext

// State: drag-over
className="border-primary bg-primary/5 ring-2 ring-primary/30"
// → "Drop it here" text change

// State: uploading (after file selected + form submitted)
className="border-border/50 bg-muted/30"
// → Spinner or animated progress indicator, "Uploading..." text

// State: processing (polling)
className="border-border/50 bg-muted/30"
// → Animated dots or progress pulse, "Reading your resume..." text

// State: file selected (idle, file chosen, not yet submitted)
className="border-primary/40 bg-primary/5"
// → File icon + file.name, file size, "Click to change" secondary text

// State: done → handled by router.push (navigates away)
// State: failed
className="border-destructive/50 bg-destructive/5"
// → Error icon + error message
```

**Key addition:** An `UploadCloud` or `FileText` lucide icon in the idle state (currently no icon). Icon size: `h-8 w-8 text-muted-foreground` idle, `h-8 w-8 text-primary` on drag-over.

**Whether to extract to separate component:** Yes. Recommended by Claude's Discretion. It separates the visual state machine from the page's async polling logic, making both easier to reason about.

## Common Pitfalls

### Pitfall 1: Changing `--color-primary` Without Checking Console Impact

**What goes wrong:** `--color-primary` in `packages/ui/src/styles/theme.css` is shared between apps/web AND apps/console. If the primary colour changes to a warm accent for the public site, the console's BD lead card "Strong match" badge, selected button states, and any primary-colored console UI elements also change.
**Why it happens:** Theme is at the shared package level.
**How to avoid:** Two options: (A) Use a web-specific CSS variable override in `apps/web/app/globals.css` that re-maps `--color-primary` to the warm accent, leaving theme.css unchanged; (B) Accept that the console also gets the colour change (the console is a dense internal tool — colour matters less). Option A is safer.
**Recommendation:** Apply primary colour change as a web-specific override in `apps/web/app/globals.css` under `:root { }`.

### Pitfall 2: Overlay Gradient Uses Wrong Background Token

**What goes wrong:** The new locked-jobs overlay uses `from-background` (Tailwind utility). If `--color-background` in theme.css is pure white but the warm body override is in a CSS rule on `body {}`, the gradient will fade to pure white while the page background is warm — creating a colour mismatch at the fade edge.
**Why it happens:** CSS custom property `--color-background` is set in `@theme {}` (theme.css), not overridden in `:root {}` in globals.css. The `from-background` Tailwind utility reads the theme.css value.
**How to avoid:** Override `--color-background` in `:root {}` in `apps/web/app/globals.css` instead of using a `body { background-color: ... }` rule. Then both the page and the gradient use the same value.

### Pitfall 3: `transition-shadow` Is Not a Standard Tailwind Utility

**What goes wrong:** Writing `transition-shadow` expecting it to transition `box-shadow`. In Tailwind v4, the correct class is `transition-[box-shadow]` for shadow-only transitions, or use the multi-property `transition-[color,box-shadow]`.
**Why it happens:** `transition-colors` and `transition-opacity` are standard; `transition-shadow` is not in Tailwind's built-in list.
**How to avoid:** Use `transition-[color,box-shadow,transform]` for the job card hover that needs colour + shadow + lift. Or define a local utility class in globals.css.

### Pitfall 4: Card Component Default `py-6` vs Custom `p-4`

**What goes wrong:** The shared `Card` component has `py-6` and `gap-6` baked in. When JobCard overrides with `p-4`, it suppresses the py but not the gap-6. This can create unexpected spacing inside the card when multiple children are present.
**Why it happens:** The `p-4` className overrides `py-6` (more specific last wins in Tailwind), but `gap-6` still applies to the flex column layout.
**How to avoid:** The JobCard wraps the Card's single `<div className="space-y-2">` child. The `gap-6` would apply between flex children — since there's only one direct child div (the `space-y-2` wrapper), `gap-6` has no effect. This is actually fine. No change needed here.

### Pitfall 5: Dropzone Drag Events on `<label>` Require `preventDefault` on `onDragOver`

**What goes wrong:** If `onDragOver` doesn't call `event.preventDefault()`, the browser won't allow the `onDrop` event to fire (it's the default HTML5 drag-and-drop behaviour).
**Why it happens:** Browser security model — you must signal that the drop target accepts files.
**How to avoid:** Always include `onDragOver={e => e.preventDefault()}` (or combined with state update) on the dropzone element.
