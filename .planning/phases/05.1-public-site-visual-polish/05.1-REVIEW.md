# Phase 05.1: Code Review Report

**Reviewed:** 2026-06-15T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15

## Summary

This phase delivers visual polish to the public candidate site: hero typography, job card hover effects, filter bar focus rings, locked-jobs overlay, auth forms, onboarding flows, a resume dropzone, and the profile edit page. The CSS token overrides and structural changes are sound. However, five blockers were identified covering an unhandled async error in the polling loop, hardcoded credentials in a production form, missing auth tokens on protected API calls, a security gap in the `safeHref` URL sanitiser, and a broken interval on unmount. Seven warnings cover logic bugs, inconsistent state behaviour, and missing error guards that will surface in production usage.

## Critical Issues

### CR-01: Hardcoded credentials pre-fill production login form

**File:** `apps/web/app/login/page.tsx:22-23`
**Issue:** `email` and `password` state are initialised to `'alex@example.com'` and `'password'`. These values appear in the rendered `<input>` elements by default. Any user who lands on the login page without clearing the fields will submit someone else's credentials — or, more likely, real users will read these as hints and adopt `password` as their password. Beyond the obvious UX embarrassment, this is a security defect: pre-filling a password field in the DOM leaks a credential into browser autofill, accessibility tools, and any JavaScript that reads the DOM.
**Fix:**
```tsx
const [email, setEmail] = useState('')
const [password, setPassword] = useState('')
```
Remove the hardcoded values entirely. Use MSW-provided cookies or `NEXT_PUBLIC_DEV_EMAIL` / `NEXT_PUBLIC_DEV_PASSWORD` env vars if quick dev login is genuinely needed, gated behind `process.env.NODE_ENV === 'development'`.

### CR-02: Polling interval not cleared on upload error — timer leak and stale state mutation

**File:** `apps/web/app/onboarding/1/page.tsx:26-53`
**Issue:** The polling `useEffect` starts a `window.setInterval` whenever `parseId` is set. The cleanup function (`return () => window.clearInterval(timer)`) is correct for the happy path, but the error branch inside the interval callback at line 33 calls `window.clearInterval(timer)` and returns early. The problem is that `timer` is captured from the `window.setInterval` call at line 28. `setInterval` returns an `id` synchronously, so the capture is fine — **but** the `setStatus('failed')` + `setError(...)` calls at lines 32-34 and 45-47 mutate React state on a component that may have already unmounted (e.g., if the user navigates away during the poll). React will throw an "update on unmounted component" warning and the cleanup closure will attempt to `clearInterval` a timer that was already cleared inside the callback, producing a harmless double-clear. More critically, if `router.push('/onboarding/2')` at line 43 fires and the component unmounts before the cleanup runs, the effect may fire one more interval tick on the now-unmounted tree.

The real blocker is that there is **no try/catch** around the `fetch` inside the interval callback. If the network request throws (e.g., `TypeError: Failed to fetch`), the exception propagates out of the async interval callback unhandled, silently crashing the interval without clearing it — the interval then continues firing indefinitely, spamming the API and leaking the timer.

**Fix:**
```tsx
useEffect(() => {
  if (!parseId) return
  let cancelled = false

  const timer = window.setInterval(async () => {
    try {
      const response = await fetch(
        `${API_BASE}/api/v1/candidate/profile/resume/status/${parseId}`,
      )
      if (cancelled) return
      if (!response.ok) {
        setStatus('failed')
        setError('Resume parsing failed. You can continue manually.')
        window.clearInterval(timer)
        return
      }
      const data = (await response.json()) as ResumeParseStatus
      if (cancelled) return
      if (data.status === 'complete') {
        if (data.profile_snapshot) {
          localStorage.setItem(
            'candidate_profile_snapshot',
            JSON.stringify(data.profile_snapshot),
          )
        }
        window.clearInterval(timer)
        router.push('/onboarding/2')
      } else if (data.status === 'failed') {
        setStatus('failed')
        setError('Resume parsing failed. You can continue manually.')
        window.clearInterval(timer)
      } else {
        setStatus('processing')
      }
    } catch {
      if (!cancelled) {
        setStatus('failed')
        setError('Resume parsing failed. You can continue manually.')
      }
      window.clearInterval(timer)
    }
  }, 800)

  return () => {
    cancelled = true
    window.clearInterval(timer)
  }
}, [parseId, router])
```

### CR-03: All protected API calls send no auth token — every authenticated request will receive 401

**File:** `apps/web/app/onboarding/1/page.tsx:69-78`, `apps/web/app/profile/edit/page.tsx:104-108`, `apps/web/app/profile/edit/page.tsx:157-160`
**Issue:** The token stored by `CandidateAuthProvider.signIn` at `localStorage.getItem('candidate_access_token')` is never read by any of the API calls in the reviewed files. `onboarding/1/page.tsx` POST to `/api/v1/candidate/profile/resume` (line 69), the profile GET (line 104), the profile PUT (line 157), and the onboarding poll GET (line 29) all omit the `Authorization` header. When the mock layer is removed and the real FastAPI backend enforces JWT auth, every one of these calls will fail with 401. The login and signup calls are intentionally unauthenticated and are correct.
**Fix:** Create a shared fetch helper that injects the token:
```tsx
// apps/web/app/_lib/authed-fetch.ts
export function authedFetch(url: string, init: RequestInit = {}): Promise<Response> {
  const token = localStorage.getItem('candidate_access_token')
  return fetch(url, {
    ...init,
    headers: {
      ...(init.headers ?? {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
  })
}
```
Replace all `fetch(...)` calls in authenticated routes with `authedFetch(...)`.

### CR-04: `safeHref` passes `http:` URLs without any origin validation — open redirect and XSS vector

**File:** `apps/web/app/profile/edit/page.tsx:38-47`
**Issue:** The function allows any `http:` or `https:` URL. This means a value like `http://evil.com/xss` stored as `github_url` or `linkedin_url` in the backend would be returned to the page and placed into an anchor tag's `href`. While the rendered links are not in the reviewed file, the function is the last line of defence before `href` assignment. Because `http:` is permitted, a MITM-attacker or a compromised backend can inject arbitrary navigations to off-brand or phishing URLs via this trust. At minimum, GitHub URLs should be restricted to `github.com` and LinkedIn URLs to `linkedin.com`.

Additionally, the catch branch at line 43 allows relative URLs (`url.startsWith('/')`). A value like `/evil-path` stored in the backend profile would be returned unchanged. This is unlikely to be harmful today but is unintentional widening of the trusted set.
**Fix:**
```tsx
const ALLOWED_ORIGINS: Record<'github_url' | 'linkedin_url', string> = {
  github_url: 'https://github.com',
  linkedin_url: 'https://www.linkedin.com',
}

function safeHref(
  url: string | null | undefined,
  field: 'github_url' | 'linkedin_url',
): string | undefined {
  if (!url) return undefined
  try {
    const parsed = new URL(url)
    const allowed = ALLOWED_ORIGINS[field]
    if (
      (parsed.protocol === 'https:' || parsed.protocol === 'http:') &&
      (parsed.origin === allowed ||
        parsed.origin === allowed.replace('https://', 'http://'))
    ) {
      return url
    }
  } catch {
    // not a valid absolute URL — reject
  }
  return undefined
}
```

### CR-05: `formatComp` called twice per render — but more critically, `!min` treats `0` as falsy

**File:** `apps/web/app/jobs/_components/job-card.tsx:15-18`, `50-53`
**Issue:** `formatComp` is called twice at lines 50 and 52 (once to check truthiness, once to render the value). This is a minor duplication but not the blocker — the blocker is the guard `if (!min) return null` at line 16. This uses a falsy check, which means a `compensation_min` of `0` (valid for unpaid internships or contract-with-equity roles) returns `null` and hides the compensation entirely rather than showing `$0`. This is a data correctness bug.

For the double-call: the component should compute the value once.
**Fix:**
```tsx
function formatComp(min: number | null, max: number | null): string | null {
  if (min === null || min === undefined) return null  // explicit null check
  const fmt = (n: number) => `$${(n / 1000).toFixed(0)}k`
  return max !== null && max !== undefined && max !== min
    ? `${fmt(min)}–${fmt(max)}`
    : fmt(min)
}

// In JSX — compute once:
const comp = formatComp(job.compensation_min, job.compensation_max)
// ...
{comp && <p className="text-sm text-muted-foreground">{comp}</p>}
```

## Warnings

### WR-01: `handleSubmit` in `onboarding/1/page.tsx` has no try/catch — uncaught network error crashes silently

**File:** `apps/web/app/onboarding/1/page.tsx:56-83`
**Issue:** The `handleSubmit` async function calls `fetch` but never wraps it in try/catch. If the network is unavailable or the request throws a `TypeError`, the exception propagates to the React event handler, which in Next.js produces an unhandled rejection. `isSubmitting` / `status` stay in `'uploading'` forever, locking the UI. The same pattern exists in `login/page.tsx` (line 32) and `signup/page.tsx` (line 35).
**Fix:**
```tsx
async function handleSubmit(event: FormEvent<HTMLFormElement>) {
  event.preventDefault()
  if (!file) { setError('Choose a resume file first.'); return }
  setError(null)
  setStatus('uploading')
  try {
    const formData = new FormData()
    formData.append('file', file)
    const response = await fetch(`${API_BASE}/api/v1/candidate/profile/resume`, {
      method: 'POST',
      body: formData,
    })
    if (!response.ok) {
      setStatus('failed')
      setError('Resume upload failed. You can continue manually.')
      return
    }
    const data = (await response.json()) as { parse_id: string }
    setParseId(data.parse_id)
    setStatus('processing')
  } catch {
    setStatus('failed')
    setError('Resume upload failed. Check your connection and try again.')
  }
}
```
Apply the same pattern in `login/page.tsx` and `signup/page.tsx`.

### WR-02: Profile edit `Select` components use `defaultValue` instead of controlled `value` — form reset doesn't update them

**File:** `apps/web/app/profile/edit/page.tsx:322-338`, `342-358`
**Issue:** The `remote_preference` and `seniority` `<Select>` components use `defaultValue={profile?.remote_preference ?? undefined}` (lines 322, 342). `defaultValue` is an uncontrolled prop — once the component mounts with the initial render (where `profile` is undefined because the query hasn't resolved yet), the `defaultValue` becomes `undefined` and is never updated when `profile` loads. The `form.reset(...)` call (line 128) correctly sets the RHF field values, but the shadcn `<Select>` component reads its visual state from the Radix uncontrolled tree, not from RHF's registered value, because no `{...form.register(...)}` or `Controller` is wiring them together.

This means a user who loads the page will see blank selects even after their profile loads, and submitting the form will send the correct RHF value (set by `onValueChange` → `form.setValue`) only if they interact with the select first. Any field they leave untouched will revert to `undefined` in the submit payload.
**Fix:** Use RHF `Controller` or `useController`:
```tsx
import { Controller } from 'react-hook-form'

<Controller
  control={form.control}
  name="remote_preference"
  render={({ field }) => (
    <Select value={field.value ?? ''} onValueChange={field.onChange}>
      <SelectTrigger><SelectValue placeholder="Select preference…" /></SelectTrigger>
      <SelectContent>
        <SelectItem value="remote_only">Remote only</SelectItem>
        <SelectItem value="hybrid">Hybrid</SelectItem>
        <SelectItem value="onsite">On-site</SelectItem>
        <SelectItem value="flexible">Flexible</SelectItem>
      </SelectContent>
    </Select>
  )}
/>
```
Apply identically for `seniority`.

### WR-04: `candidate-auth-context` stores parsed `candidate_data` JSON without type validation — prototype pollution risk

**File:** `apps/web/app/_components/candidate-auth-context.tsx:21`
**Issue:** `JSON.parse(stored)` is cast directly to `{ id: string; email: string }` with no runtime validation. A poisoned `localStorage` value (from XSS, a browser extension, or cross-origin storage attack) can set `candidate_data` to `{"__proto__": {"isLoggedIn": true}}` or include unexpected properties. The comment claims `try/catch` "guards against prototype pollution" but it does not — `try/catch` only catches JSON parse syntax errors, not semantic attacks. The parsed object is set as state and then passed to every consumer through context. If the object has an `id` or `email` property containing a script payload, those values can flow into rendered output (e.g., the avatar fallback at `site-nav.tsx:50`).
**Fix:**
```tsx
try {
  const parsed = JSON.parse(stored)
  if (
    parsed &&
    typeof parsed === 'object' &&
    typeof parsed.id === 'string' &&
    typeof parsed.email === 'string'
  ) {
    setCandidate({ id: parsed.id, email: parsed.email }) // whitelist-copy, not spread
  }
} catch { /* corrupt — ignore */ }
```

### WR-05: `filter-bar.tsx` filter tag remove buttons for `location` and `skills` are missing focus rings

**File:** `apps/web/app/jobs/_components/filter-bar.tsx:140-144`, `148-152`

### WR-06: `JobCard` applies `aria-hidden` to the wrapping `<Link>` without removing it from focus order

**File:** `apps/web/app/jobs/_components/job-card.tsx:29`
**Issue:** `<Link ... aria-hidden={isLocked}>` sets `aria-hidden` on the link element when it is locked, which hides it from the accessibility tree. However `tabIndex={isLocked ? -1 : undefined}` removes it from tab order. `aria-hidden` on an interactive element that can still receive focus via pointer (since `pointer-events-none` is only on the `Card`, not the wrapping `Link`) is an accessibility violation: if a user somehow reaches the element, a screen reader will ignore it while the element is still technically focusable via click on overlapping content. More practically, `aria-hidden={isLocked}` evaluates to `aria-hidden={false}` when not locked, which while harmless is redundant. The real gap is that `aria-hidden={true}` plus `tabIndex={-1}` in combination does not prevent pointer-activated focus in all browser/AT combinations.
**Fix:** Replace both attributes with a single `inert` prop (React 19 supports it natively):
```tsx
<Link href={`/jobs/${job.id}`} className="group block" inert={isLocked || undefined}>
```
If React 18 support is needed, keep `tabIndex={isLocked ? -1 : undefined}` and `aria-hidden={isLocked || undefined}` (conditional so `false` is never emitted).

### WR-07: `onboarding/1/page.tsx` redirect guard fires on the initial render before localStorage is hydrated

**File:** `apps/web/app/onboarding/1/page.tsx:21-23`
**Issue:** `useEffect(() => { if (!isLoggedIn) router.replace('/signup') }, [isLoggedIn, router])` runs after the first render. On that first render, `isLoggedIn` is `false` because `CandidateAuthProvider` reads localStorage in a separate `useEffect` that also runs after the first render. The auth state is not available synchronously. This creates a race: a logged-in user who navigates directly to `/onboarding/1` will be redirected to `/signup` before the token is read from localStorage. The same defect exists in `onboarding/2/page.tsx:36-38` and `profile/edit/page.tsx:98-100`.
**Fix:** Add a loading/initialised state to `CandidateAuthProvider` that is `false` until the localStorage hydration effect has run, then gate the redirect on both `!isLoggedIn && isInitialised`:
```tsx
// In CandidateAuthProvider
const [isInitialised, setIsInitialised] = useState(false)
useEffect(() => {
  // ...existing hydration logic...
  setIsInitialised(true)
}, [])
// Expose isInitialised in context value
```
```tsx
// In protected pages
useEffect(() => {
  if (isInitialised && !isLoggedIn) router.replace('/signup')
}, [isLoggedIn, isInitialised, router])
if (!isInitialised) return null // avoid flash of protected content
```

### IN-02: Test files use filesystem-read pattern rather than component rendering — fragile coupling to class strings

**File:** `apps/web/src/__tests__/visual-polish.test.tsx:1-96`, `visual-polish-forms.test.tsx:1-69`, `visual-polish-final.test.tsx:1-45`
**Issue:** All tests assert on raw file content via `fs.readFileSync`. This means tests pass when a class string is present anywhere in the file — including in comments or dead code — and will fail if the class string is changed to a semantically identical alternative (e.g., `transition-[color,box-shadow,transform]` spelled differently). The test for `transition-all` at `visual-polish-final.test.tsx:25-44` walks the entire `APP_DIR` tree at test time, which will include test files themselves — if a test file ever contains the string `transition-all` in a comment or assertion the test will falsely fail. These are effectively linter checks, not component behaviour tests.
**Fix:** This approach is acceptable for a small team doing polish validation, but note that these tests do not verify runtime behaviour. Consider adding at least one `@testing-library/react` rendering test per critical component to catch runtime errors (missing imports, context mismatches).
