## Spacing Scale

Inherited from Phase 3 (identical to Phase 2). No new scale changes.

**Phase 4–specific spacing notes:**

- Search filter sidebar: `w-[260px]` fixed width, collapsible. Inner padding `px-4 py-4`.
- Results grid column: `flex-1 min-w-0, overflow-y-auto`. Candidate cards `gap-2` in a `flex flex-col`.
- Candidate result card: `px-4 py-3` (same density as Phase 3 client/req list rows).
- `CandidateProfileSheet`: inherits Phase 3 slide-over `w-[560px]` with `px-6 py-4` body.
- Admin tab content area: `px-6 py-6` (matches Phase 3 requisition detail page).
- Admin overview cards: 4-column grid `grid grid-cols-4 gap-4` on desktop; `grid-cols-2` below xl.
- Admin split-view prompt editor: left panel `w-[280px]` flex-shrink-0, right panel `flex-1`.
- Engagement sequence steps: `flex flex-col gap-4` between StepEditor cards.
- Filter chips row: `flex flex-wrap gap-2` with `mt-3` top margin from search form.

**Phase 4 micro-spacing exceptions (badge padding and dense UI elements — same precedent as Phase 2 ICP badge `px-2.5 py-1`):**

| Value | px | Location | Justification |
|-------|----|----------|---------------|
| `px-1.5 py-0.5` | 6px / 2px | Rank badge (#1/#2/#3) | Badge/pill internal padding — requires sub-4 micro-spacing to maintain pill density without excess whitespace; identical precedent to Phase 2 ICP score badge |
| `mt-0.5` | 2px | CandidateResultCard Row 2 (title/company line) | Optical micro-gap between name row and subtitle row in dense card format |
| `gap-1.5` | 6px | Results header active filter chips | Dense chip row — 4px gap collapses chips visually; 8px gap is too wide for inline chip rows |
| `py-0.5` | 2px | AdminEventsTab EventRow | Dense table-row internal padding in a monitoring log — matches Phase 2 shortcut overlay kbd element precedent |
| `py-2.5` | 10px | AdminPromptsTab PromptListItem | Prompt list items need slightly more vertical rhythm than `py-2` (8px) without the full `py-3` (12px) — badge padding exception |
| `pl-[10px]` | 10px | Active PromptListItem left padding (active state left-border offset) | Left border `border-l-2` (2px) is compensated by reducing padding from 12px to 10px so text stays optically aligned — same technique as Phase 2 active nav item |
| `size-1.5` / `h-1.5` | 6px | Dirty state amber dot; overview quota progress bar height | Fine decorative elements — a 4px dot is invisible; 8px is too prominent |

## Typography

Inherited from Phase 3 — 4 roles, 2 weights, unchanged.

**Phase 4–specific notes:**

- Rank badge (#1, #2, #3): 12px/600 — same exception as ICP score badge (Label/Meta size, semibold weight). Justified as primary decision signal on candidate card.
- Match reason text on card: 12px/400 (`Label / Meta` role), `text-muted-foreground`, `line-clamp-2` — same visual rhythm as suggested angle in Phase 2 lead cards.
- Availability badge: 12px/400 (`Label / Meta` role) — same as Phase 3 status badges.
- Enrichment section headings inside profile slide-over (e.g. "GitHub Signals", "Contact"): 12px/400 uppercase tracking-wider `text-muted-foreground` — section header sub-role, consistent with Phase 3 slide-over section labels.
- Prompt editor textarea: text-sm (14px) with font-mono modifier — monospace family alone differentiates editor content from body text without introducing a new size.
- Cost table cells: 14px/400 Body role. Total row: 14px/600 semibold.
- Admin card value display (Total Spend dollar amount, Quota percentage): 20px/600 (Heading role) — primary scan target within each summary card.
- Admin card label (e.g. "Total Spend (30d)", "Quota Usage"): 12px/400 (`Label / Meta` role) above value.

### Admin Quota Warning Color

- Normal (`warning=false` and `percent < 60`): Progress bar `bg-primary` (brand blue).
- Warning (`warning=true` OR `percent >= 60`): Progress bar `bg-[oklch(0.769_0.188_85.87)]` (amber, chart-2 token).
- Critical (`percent >= 90`): Progress bar `bg-destructive`.

> Note: API docstring says "Warning at 60% (not 80% SoftBlock)". The `warning` boolean in the API response is the canonical signal. Display warning color when `warning=true` OR `percent >= 60` — whichever fires first.

## Interaction Contracts

### Talent Search Submit Flow (D-02, SUP-01)

1. Supply rep fills any combination of filter fields in sidebar. Filters can be freely edited; no auto-refetch occurs.
2. Rep clicks "Search Candidates" button OR presses Enter in any field.
3. Button enters "Searching…" disabled state. Previous results remain visible.
4. GET `/api/v1/supply/candidates/search` fires with all non-empty filter params.
5. On success: results replace previous list. Active filter chips update to reflect submitted values. Result count header updates.
6. On error: previous results remain. Toast: "Search failed — try again." (Sonner error).
7. Clicking × on an active filter chip: removes that filter value from the form AND re-submits search automatically.
8. If search returns 0 results: show "No candidates found" empty state with guidance copy.

### Enrichment Flow (D-06, SUP-02)

1. Supply rep clicks "Enrich" button in `CandidateProfileSheet` header.
2. Button replaced by "Enriching…" text + spinner (no button during polling).
3. POST `/api/v1/supply/candidates/{id}/enrich` fires. Returns 202.
4. `useAsyncJob` polling: poll GET `/api/v1/supply/candidates/{id}` every 2 seconds.
   - `statusMap`: poll until `talent_pool.email_verified !== null` OR `talent_pool.github_public_repos !== null` (enrichment arrived).
   - Maximum poll duration: 30 seconds. On timeout: treat as failure.
5. While polling: GitHub Signals section, Contact email verified field, and Resume section all show Skeleton shimmer.
6. On enrichment detected: replace skeletons with enriched data. Button disappears (enrichment no longer stale). Sonner toast: "Candidate enriched."
7. On failure/timeout: "Enrichment failed — retry" text (12px/400 text-destructive) appears in header area. "Retry" link re-triggers flow.

### Ingest Submission Flows (D-10, D-11, SUP-03)

**LinkedIn (synchronous):**
1. Rep enters LinkedIn URL and clicks "Add Candidate".
2. POST `/api/v1/supply/candidates/ingest` fires. 201 response with `IngestLinkedInResponse`.
3. Form clears. Success toast: "Candidate added: [name]."
4. New `IngestJobCard` appears in Recent Jobs with status "done" and "Candidate added: [name]".
5. On error (400 = Proxycurl not configured): "LinkedIn ingest unavailable — Proxycurl key not configured. Use CSV or resume upload instead." Sonner error toast.
6. On other error: "Ingest failed — try again." toast.

**CSV (synchronous):**
1. Rep drops or selects CSV file. "Upload CSV" button enables.
2. Click → POST `/api/v1/supply/candidates/ingest/csv` multipart. 201 response with `CsvIngestResponse`.
3. Dropzone clears. Success toast: "Imported [N] candidates."
4. New `IngestJobCard` in Recent Jobs: "Imported [N] candidates, [M] duplicates skipped."
5. On error: "CSV upload failed — check file format and try again."

**Resume (asynchronous, 202):**
1. Rep drops or selects PDF/DOCX. "Upload Resume" button enables.
2. Click → POST `/api/v1/supply/resumes/upload` multipart. 202 response with `{ task_id }`.
3. Dropzone clears. New `IngestJobCard` added with status "processing" and "Parsing resume…".
4. `useAsyncJob` polls. On complete (candidate created): card updates to "done", "Candidate created: [name]".
5. On failure: card updates to "failed", "Parsing failed — [error]".

### Engagement Sequence Review/Approve Flow (SUP-05)

1. Rep navigates to `/supply/engagements`. List shows all `draft` sequences.
2. Clicking a row opens `EngagementSequenceSheet`.
3. Rep can edit any step's subject or body inline (react-hook-form controlled fields for each step).
4. Changes to steps are local-only until explicit action.
5. On "Approve Sequence":
   - If steps were edited: PATCH `/api/v1/supply/engagement/{sequence_id}` with updated steps first. Then POST `.../approve`.
   - If not edited: POST `/api/v1/supply/engagement/{sequence_id}/approve` directly.
   - On success: sheet closes; row updates status to "approved"; Sonner toast "Sequence approved."
   - On error: sheet stays open; toast: "Approval failed — try again."
6. On "Reject Sequence":
   - 5-second undo toast: "Sequence rejected. Undo" before committing.
   - After 5s (or no undo): POST `/api/v1/supply/engagement/{sequence_id}/reject`.
   - Row updates status to "rejected"; row removed from draft list on next refetch.
7. Generate from profile (if initiating from `CandidateProfileSheet`):
   - POST `/api/v1/supply/candidates/{id}/engagement/generate` with optional `{ requisition_id }`.
   - `useAsyncJob` polls GET `/api/v1/supply/candidates/{id}/engagement` every 2 seconds until a `draft` sequence appears.
   - On done: "Generation complete — Review sequence" link appears (navigates to `/supply/engagements`).

### Admin Prompt Save Flow (ADM-05, D-16)

1. Admin selects a prompt from the left panel. Right panel loads content via GET `/api/v1/monitoring/prompts/{name}`.
2. Admin edits textarea. `isDirty` state becomes true. "• Unsaved changes" indicator appears.
3. "Save Prompt" button enables (accent blue). "Reset" button enables.
4. On "Save Prompt" click:
   - Button enters "Saving…" disabled state.
   - PUT `/api/v1/monitoring/prompts/{name}` with `{ content: editedContent }`.
   - On success: Sonner toast "Prompt saved." `isDirty` clears. Dirty indicator disappears.
   - On error: Sonner error toast "Failed to save prompt — try again." Textarea content preserved.
5. On "Reset" click:
   - If dirty: Sonner toast with action: "Discard changes? Undo" — after 3 seconds (no undo window; short wait): reload original content from cache. `isDirty` clears.
   - If not dirty: no action (button disabled).
6. If user clicks a different prompt while dirty: toast prompt "Unsaved changes — save or discard before switching." Prevent navigation (keep current prompt selected until resolved). Two inline buttons: "Save" / "Discard".

### Admin Tab Navigation (D-14)

Tab value is stored in URL as `?tab=` search param. On tab click: `router.push(pathname + '?tab=' + value)`. Each tab content mounts lazily (only fetches when tab is active). Clicking a summary card on Overview navigates to the relevant tab by pushing the search param.

### Shortlist Actions from CandidateProfileSheet (SUP-04)

When `CandidateProfileSheet` is opened from a shortlist row (`source="shortlist"`, `requisition_id` set), the quick action bar appears with "Approve Candidate" / "Hold Candidate" / "Pass on Candidate".

Flow is identical to Phase 3 shortlist table row actions:
1. Click action → optimistic badge update on shortlist row behind sheet.
2. PATCH `/api/v1/supply/shortlists/{submission_id}`.
3. Sonner 5-second undo toast.
4. Sheet remains open after action.
